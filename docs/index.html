Simple Drive.

One API, four interchangeable storage backends — S3-compatible object storage, a database table, the local filesystem, an FTP server — behind a single two-method contract. And S3 is spoken in raw HTTP, authenticated by a hand-rolled AWS Signature V4 signer: no S3 client, no AWS SDK, nothing but net/http, openssl and the specification.

The problem

Not “can it store a blob?” — “can you swap where it stores it, and sign the request yourself?”

Storing bytes is the easy part. Two constraints make this project actually interesting, and both of them are structural rather than incidental.

Constraint 1

No S3 libraries — at all the core challenge

The brief forbids the AWS SDK and every S3 client. So the S3 backend speaks the S3 REST protocol directly over Net::HTTP, and every request is authenticated by a Signature V4 implementation written from the AWS specification using only openssl and digest. Get one byte of the canonical request wrong — a header out of sort order, a stray space, the wrong percent-encoding — and the service answers 403 with no explanation of which byte.

app/services/storage/sig_v4.rb · app/services/storage/s3_backend.rb

Constraint 2

A seam that survives four implementations open/closed

Four backends with genuinely different physics — an HTTP object store, a SQL table, a POSIX filesystem, an FTP session — have to sit behind one interface without leaking a single detail upward. The test of the abstraction isn't that four fit today; it's that the fifth costs one new class and one factory entry, with controllers, models, routes and the other backends untouched.

Architecture

One request path, one factory, four adapters

Every request passes the same Bearer filter, lands on one of two endpoints, and reaches storage only through Storage.backend(name). The controllers never learn which backend is active — and never learn what a backend failure looked like, because the error hierarchy is mapped to HTTP in exactly one place.

The request lifecycle. create writes to the currently configured backend; show routes to the backend recorded on the blob itself.

The whole contract, in two methods. put(id, bytes) persists raw bytes under an opaque identifier; get(id) returns raw bytes or raises Storage::NotFound. Backends never interpret the id, never transform the bytes, and raise only from a shared hierarchy — Storage::Error, NotFound, ConfigurationError — which the base controller maps to 502 / 404 / 500 in one place.
STORAGE_BACKEND=s3

S3-compatible raw HTTP

Path-style addressing (endpoint/bucket/key) over Net::HTTP, signed per request by Storage::SigV4. Path-style keeps one client compatible with AWS S3, minio, DigitalOcean Spaces and Linode Object Storage alike. The object key is the fully percent-encoded id, slash included, so every id maps to exactly one unambiguous key segment.

s3_backend.rb · from_config validates endpoint, bucket, keys

STORAGE_BACKEND=database

Database table separate table

Payload bytes land in a dedicated blob_contents table with its own model — never in the tracking table. Hot metadata stays small and fast, and the payload lifecycle is decoupled from the metadata lifecycle.

database_backend.rb · db/migrate/*_create_blob_contents.rb

STORAGE_BACKEND=local

Local filesystem traversal-proof

One config value: the root directory. Files are named by the SHA-256 of the id, sharded two levels deep to keep directories small, and written to a temp file that is atomically renamed into place — so readers never observe a partial blob and user input never reaches the filesystem as a path.

local_backend.rb · root/<aa>/<bb>/<sha256>

STORAGE_BACKEND=ftp

FTP server bonus

stdlib net/ftp, one connection per operation, blobs stored under base_dir by SHA-256 name. The connection factory is injectable, which is what lets the unit tests drive the whole backend — including the 550 → NotFound mapping — with no live server.

ftp_backend.rb · ftp_factory: injectable

Data model: metadata and payload never share a table

The tracking table holds no data. The database backend gets its own table. And every metadata row records which backend holds its payload — the single column that makes reconfiguration safe.

Uniqueness is enforced twice on purpose: an application check gives the friendly 409 fast path, a database unique index is the real guarantee under concurrency.

The centerpiece

AWS Signature V4, written from the specification

No AWS SDK, no S3 client, no signing gem — Storage::SigV4 requires exactly openssl and digest. It builds the canonical request, derives a four-stage scoped signing key, and returns the complete header set including Authorization. It is not a rough approximation that happens to work against one server: the test suite reproduces AWS's own documented example signature, byte for byte.

The derived signing key is scoped to one day, one region, one service — the long-term secret never signs a request directly, so a leaked derived key has minimal blast radius.

The proof

AWS's documented example, reproduced exactly

The first unit test signs the request from AWS's own “Create a signed AWS API request” documentation — IAM ListUsers, credentials AKIDEXAMPLE, frozen at 2015-08-30T12:36:00Z — and asserts the resulting Authorization header equals the published one. That single equality validates the entire pipeline at once: canonical request, string-to-sign, key derivation and final HMAC.

The details that break signatures

Three rules that are easy to get subtly wrong

Encoding. SigV4.uri_encode implements RFC 3986 unreserved encoding — everything outside A-Z a-z 0-9 - _ . ~ is percent-encoded, operating on bytes so UTF-8 ids encode correctly.

Canonicalisation. Header names are lower-cased, values trimmed and inner whitespace squeezed, then sorted — because the server recomputes the same string and compares hashes.

Payload hash. For the s3 service the signer adds x-amz-content-sha256 to the signed header set, so the body is bound into the signature rather than merely accompanying it.

sig_v4.rb · uri_encode · canonicalize_headers · signing_key

Tested on the wire, not just in a unit. test/services/s3_backend_test.rb stands up an in-process fake S3 server and drives the backend at it over real HTTP — the fake asserts the SigV4 Authorization header, the payload hash and the percent-encoded object key as they arrive. The backend was then verified end-to-end against a real minio server under Docker.
Decisions & guarantees

Five choices that are correctness or security, not taste

Each one is a small amount of code doing a specific job, and each has a test that fails if the guarantee is removed.

Correctness

One transaction, no orphans

The metadata insert and the backend write share a single Blob.transaction. If put raises — S3 unreachable, disk full, FTP refused — the transaction rolls back and no metadata row survives pointing at bytes that were never stored. A 409 for a duplicate id is checked first, and again caught from the database's unique index for the concurrent case.

blobs_controller.rb#create · rollback test in controller tests

Operability

Backend routing is per blob

Every metadata row records the backend that stored it, and retrieval calls blob.storage — the backend named on that row, not the currently configured one. Switching STORAGE_BACKEND changes where new blobs go and strands nothing: everything written before the change stays retrievable.

blob.rb#storage · blobs.backend column

Security

Ids can't escape the filesystem

The local backend never sanitizes user input into a path — it doesn't use user input as a path at all. The filename is SHA-256(id), sharded two levels. An id of ../../etc/passwd is just another string that hashes to a hex name inside the root, which is asserted directly by a traversal test.

local_backend.rb#path_for · traversal test

Input handling

Strict Base64, or 400

Decoding uses Base64.strict_decode64: canonical Base64 only. A bad alphabet, bad padding or stray whitespace is rejected with 400 instead of being silently decoded into corrupted bytes. The empty string is deliberately still valid — the empty blob is a real blob, so presence of the data key is checked separately from its emptiness.

blobs_controller.rb#decode_base64!

Auth

Constant-time, and unforgettable

Bearer auth is a before_action on the base controller, so no endpoint can be added that forgets it, and comparison goes through ActiveSupport::SecurityUtils.secure_compare — closing the timing side channel that makes a token guessable byte by byte. Rejections carry a WWW-Authenticate: Bearer header.

application_controller.rb#authenticate!

Interface

Ids stay opaque, all the way down

Ids may be UUIDs, path-like strings or arbitrary unicode. The route is a wildcard (get "blobs/*id", format: false), so slashes and dots survive routing intact rather than being read as nesting or a format extension — and no layer below ever interprets id semantics.

config/routes.rb · path-id test

Run it

Two ways in — local in a minute, or against a real S3 server

Ruby 3.1+ (.ruby-version targets 3.3). Everything is environment-driven and .env.example documents every variable; the default backend is local, so nothing external is required to see it work. 

# 1 — boot it locally
$ bundle install
$ bin/rails db:prepare

$ export SIMPLE_DRIVE_TOKEN=$(openssl rand -hex 32)
$ export STORAGE_BACKEND=local   # local | database | s3 | ftp

$ bin/rails server

# 2 — store a blob (Base64 payload, opaque id)
$ curl -X POST http://localhost:3000/v1/blobs \
    -H "Authorization: Bearer $SIMPLE_DRIVE_TOKEN" \
    -H "Content-Type: application/json" \
    -d '{"id": "docs/hello.txt",
         "data": "SGVsbG8gU2ltcGxlIFN0b3JhZ2UgV29ybGQh"}'

# 201 Created
# {"id":"docs/hello.txt","size":"27",
#  "created_at":"2026-08-06T11:18:23Z"}

# 3 — read it back (note the path-like id)
$ curl http://localhost:3000/v1/blobs/docs/hello.txt \
    -H "Authorization: Bearer $SIMPLE_DRIVE_TOKEN"

# 200 OK — same bytes, re-encoded
# {"id":"docs/hello.txt","data":"SGVsbG8g...",
#  "size":"27","created_at":"2026-08-06T11:18:23Z"}

# 4 — the suite: 34 tests, 72 assertions
$ bin/rails test
# Or: the whole thing against a real S3 server
$ docker compose up --build

# brings up three services:
#   app         :3000   the API (STORAGE_BACKEND=s3)

$ curl -X POST http://localhost:3000/v1/blobs \

         "data":"SGVsbG8gU2ltcGxlIFN0b3JhZ2UgV29ybGQh"}'

Taking it to production

The same seam, at enterprise scale

A reference implementation earns its keep by being shaped like the real thing. Below is how Simple Drive would grow into production infrastructure — and, for each step, the seam that already exists in the code which it hangs off. That's the point: none of this requires reworking the core, because the adapter boundary, the per-blob routing column and the single auth method were put there for exactly this.

Target topology — not built. Every box is either a component that exists today or an adapter that plugs into the existing factory.

STEP 01

Horizontal replicas behind a load balancer

The API is already stateless: payload lives in the backend, metadata in the database, and no request depends on anything held in a process. Scaling out is adding replicas behind a load balancer — with the caveat that the local backend is the one option that isn't shareable, so production picks an object-store backend.

Existing seam — no per-process state; blobs table is the only coordination point

STEP 02

Per-client tokens and scoped access

The single shared bearer token becomes a per-client credential with scopes — read vs. write, tenant-limited, revocable, rotatable. This is contained work precisely because authentication is one private method on the base controller that every endpoint already inherits; the change is inside authenticate!, plus a table of clients.

Existing seam — ApplicationController#authenticate! (single before_action)

STEP 03

DELETE and a paginated list endpoint

delete(id) joins the backend contract, implemented once per adapter, and the controller mirrors create's ordering in reverse — remove the backend bytes first, then the metadata row, so a failure leaves a retrievable blob rather than a dangling record. Listing reads the metadata table alone, so it never touches a backend and paginates cheaply.

Existing seam — Storage::BaseBackend contract · blobs table already carries every listable field

STEP 04

Streaming and multipart uploads

Today put takes a String of bytes, which caps practical object size at what fits in memory. The contract widens to accept an IO, and the S3 adapter grows multipart upload — initiate, sign and send each part, complete. The signer needs no redesign: it already computes a payload hash per request, which is exactly the per-part unit.

Existing seam — S3Backend#request builds raw Net::HTTP requests · SigV4 signs per request

STEP 05

At-rest encryption and per-tenant isolation

Envelope encryption sits at the adapter boundary — encrypt in put, decrypt in get, with keys from a KMS and the key id recorded alongside the metadata. Tenant isolation is a prefix or bucket per tenant, and that's a change to a single private method: each backend already derives its storage location in one place (object_path, path_for, remote_path).

Existing seam — one id→location method per backend · opaque ids, never interpreted

STEP 06

Azure Blob or GCS — the identical recipe

A new provider is one class and one line: implement put/get, add an entry to Storage::BACKENDS, write its test. Controllers, models, routes and the four existing backends stay untouched — the property the abstraction was built to have, and the reason the no-SDK constraint didn't cost anything structurally.

Existing seam — Storage::BACKENDS factory hash · adding a backend touches one class

STEP 07

Observability worth paging on

Structured logs with a request id, per-backend latency and error-rate metrics, and traces that span the controller and the outbound backend call. The natural instrumentation points already exist: the storage factory is the one place a backend call originates, and rescue_from is the one place a backend failure becomes an HTTP status.

Existing seam — Storage.backend factory · centralised rescue_from error mapping

STEP 08

Tiering and replication across backends

Hot blobs in S3, cold blobs in cheaper storage, or the same blob replicated across two providers. This is possible only because routing is recorded per blob rather than globally: a background worker copies the bytes, updates blobs.backend for that row, and reads transparently follow — no migration window, no client change, no downtime.

Existing seam — blobs.backend is per-row · blob.storage resolves at read time

STEP 09

Content-addressed storage and dedup

The local backend already names files by SHA-256. Hashing the content instead of the id turns that into content addressing: identical payloads collapse to one stored object, the metadata row keeps the reference count, and a duplicate upload becomes a metadata write with no bytes moved.

Existing seam — BaseBackend#digest_name (SHA-256) shared by local and FTP

Proven, on every run

34 tests across test/services/ and test/controllers/, green on a clean Linux machine in CI on every push and pull request.

  • The signer is correct, not merely accepted. AWS's officially documented example signature is reproduced byte-for-byte, along with the URI-encoding rules and the S3 payload-hash header.
  • S3 is exercised over real HTTP. An in-process fake S3 server receives actual requests and asserts the Authorization header, payload hash and percent-encoded object key on the wire — then the same backend was run against a live minio server under Docker Compose.
  • Path traversal cannot escape the root — asserted directly with a hostile id, alongside binary round-trips and unicode ids.
  • The transaction boundary holds. A forced backend failure is asserted to leave no orphan metadata row behind.
  • Per-blob routing works. A blob written under one backend is retrieved after the configured backend changes.
  • The API contract is pinned — exact response shapes, auth rejection, strict-Base64 rejection, missing fields, duplicates, path-like ids and the empty blob.

Not built — a reference implementation, not a hardened service honest limits

Taken from the repository's own Extending the system section and stated here at the same confidence. These are scope boundaries, not oversights.

  • No DELETE and no list endpoint. The API is store and retrieve; blobs are effectively write-once.
  • One shared bearer token, not per-client credentials. There is no notion of a client, a scope, or a tenant — every caller with the token has full access.
  • No streaming or multipart. Payloads are Base64 in a JSON body and held in memory, which bounds practical object size; very large objects need the streaming work described above.
  • No encryption at rest. Bytes are handed to the backend as-is; confidentiality is whatever the underlying store provides.
  • The FTP backend is tested against an injected fake implementing Net::FTP's transfer interface, including the 550 → NotFound mapping — it has not been run against a live FTP server.
  • Verified environments are named, not assumed: macOS on Ruby 3.3.4 / Rails 7.2.3 with the local and database backends exercised end-to-end, and Docker (ruby:3.3-slim) against minio for S3.
